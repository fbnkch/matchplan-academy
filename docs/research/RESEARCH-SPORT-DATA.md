# Football data scouting: research map for deeper learning

**Research checked:** 27 October 2026

**Scope:** free or low-cost, locally runnable learning resources, role signals from first-party football employers, and concrete portfolio-grade exercises. Links were checked on the date above. Job status is time-sensitive; resource pages can move or change.

## What the current platform already covers

The existing Matchplan Academy already teaches Python and SQL basics, visualization, introductory xG, scouting comparisons, and synthetic-data projects. Its project notes correctly distinguish synthetic exercises from evidence about real players and call for video/context checks. The next layer should therefore shift from guided toy exercises toward reproducible work on public match data, explicit data contracts, failure handling, temporal validation, and decision communication. Keep the default path runnable on a laptop with Python, DuckDB/SQLite, and public files; cloud services should be optional extension work rather than a prerequisite.

## Recommended learning sequence

1. **Data semantics before models.** Inspect one StatsBomb match JSON and its documentation; record entity grain, IDs, periods, coordinate orientation, event definitions, absent fields, and attribution. Render a few actions and manually reconcile counts. Use only a small match subset initially.
2. **Reliable local data pipeline.** Keep raw inputs immutable; make ingestion deterministic and rerunnable; add file hashes, a manifest, schema/version checks, uniqueness and referential-integrity checks. Transform to Parquet/CSV and query locally with DuckDB. Add a failure-and-retry exercise before introducing a scheduler.
3. **SQL and analysis-ready tables.** Build match, team, player, and event/action models with explicit grain. Practice `lag`, `lead`, running aggregates, and partitions. Test joins for duplicate inflation and compare sampled outputs back to raw data.
4. **Communicate descriptive findings.** Create a concise match report with mplsoccer; explain what each chart can and cannot establish. If extending to tracking, use Metrica tutorial data or a small public Sportec sample and explicitly inspect coordinate and time alignment.
5. **Model probabilities responsibly.** Train a simple xG baseline, use match-based/time-aware holdouts, fit all transformations on training data only, compare calibration as well as discrimination, and state sample limits. Make a deliberately leaky version and show why its estimate is invalid.
6. **Action valuation and scouting.** Reuse standardized SPADL actions for xT/VAEP; audit action sequences and ranking sensitivity. Build a role-first shortlist with comparison group and uncertainty, then write a short decision memo that names follow-up video questions.
7. **Portfolio packaging.** Include runnable instructions, pinned dependencies, data provenance/attribution, tests and sample outputs, limitations, and a short screen-recorded or written walkthrough. Separate code/tool competence from football interpretation. Do not claim access to club data or feedback unless actually obtained.

## Curated resources (16)

Each entry gives the reason to use it and a specific action; the mapping above shows how it supports a role task.

1. **Friends of Tracking: Soccermatics for Python** — [GitHub repository](https://github.com/Friends-of-Tracking-Data-FoTD/SoccermaticsForPython). Free starter scripts associated with Friends of Tracking lectures: loading data, plotting passes/shots, a basic xG model and fit measures. **Action:** adapt one script to a new match, then replace its assumptions with an explicit data dictionary and match-level evaluation. Beginner-friendly entry, not an end-to-end production course.
2. **Uppsala/Soccermatics course notes** — [Soccermatics course repository](https://github.com/Pi03/Soccermatics). Gives mathematical framing and notes the university course’s substantial statistics, linear algebra and calculus prerequisites; also describes the course format and audience. **Action:** use its topic list to choose a deeper follow-up after the Python starter. Course access/fees and dates can change; the repository’s course description should be checked before applying.
3. **Friends of Tracking: LaurieOnTracking** — [Metrica tracking tutorials and code](https://github.com/Friends-of-Tracking-Data-FoTD/LaurieOnTracking). Four tutorial summaries cover event-plus-tracking visualization, physical summaries, pitch control, and expected possession value. **Action:** reproduce velocity or pitch-control plots on the included example, then write down sampling, orientation, and model assumptions. Treat pitch control as a model, not observed certainty.
4. **StatsBomb Open Data README** — [Hudl/StatsBomb open-data repository](https://github.com/hudl/open-data). First-party repository describes the JSON layout (competitions, matches, events, lineups, selected 360 files) and requests StatsBomb attribution/logo when publishing derived research/analysis/insights. **Action:** build a match manifest and cite the source in the report. Availability is a subset, not a complete commercial feed; inspect terms and current repository guidance before redistribution or commercial use.
5. **mplsoccer examples gallery** — [Official documentation gallery](https://mplsoccer.readthedocs.io/en/latest/gallery/). Runnable plotting examples include pass maps, heatmaps, shot freeze frames, StatsBomb 360, standardization and xT tutorials. **Action:** recreate one plot, include a clear title/legend and coordinate system, then add a hand-checked annotation. A compelling plot does not establish causality or decision value.
6. **Kloppy getting started** — [Official user guide](https://kloppy.pysport.org/user-guide/getting-started/). Introduces loading, filtering, transforming and exporting; explains event versus tracking data and provider parsers, with a public Sportec example. **Action:** load both event and tracking data for one match, standardize orientation and inspect the first/last timestamps and missing coordinates. Limit frames to control memory; standardized interfaces cannot remove provider-semantic differences.
7. **socceraction SPADL** — [SPADL documentation](https://socceraction.readthedocs.io/en/latest/documentation/spadl/spadl.html). Defines the action table, coordinate convention, action/result/bodypart values and conversion from provider event streams; notes synthetic dribbles. **Action:** convert one match and inspect five sequences around shots/goals against raw events. Conversion decisions affect downstream analysis; preserve original event IDs and report synthetic rows.
8. **socceraction VAEP** — [VAEP documentation](https://socceraction.readthedocs.io/en/latest/documentation/valuing_actions/vaep.html). Explains short-horizon scoring/conceding probabilities, game-state features and action value as changes in probabilities. **Action:** reproduce one season sample, compare top actions under a second lookback/window or minutes filter, and manually inspect examples. It is a model-based value framework, not proof of causal player contribution.
9. **scikit-learn: common pitfalls and leakage** — [Official guide](https://scikit-learn.org/stable/common_pitfalls). Explains preprocessing leakage and the use of pipelines so transformations are learned on training folds only. **Action:** implement a deliberately leaky scaler/model and a proper pipeline; compare a match-grouped holdout and explain the difference. Match/time dependence needs domain-aware splits beyond generic examples.
10. **scikit-learn cross-validation** — [Official guide](https://scikit-learn.org/stable/modules/cross_validation.html). Describes train/validation/test roles and why shuffling ordered/dependent samples may inflate estimates. **Action:** compare random event splits with match-grouped and chronological holdouts; publish the split logic. Generic K-fold is not automatically appropriate for sequential match data.
11. **scikit-learn probability calibration** — [Official guide](https://scikit-learn.org/stable/modules/calibration.html). Defines calibration curves and warns calibration should be fit independently of base-model training data; Brier score mixes calibration, resolution and outcome uncertainty. **Action:** plot reliability by probability bins with sample counts and evaluate log loss/Brier on held-out matches. Small samples make bins noisy; show counts and uncertainty.
12. **Apache Airflow task best practices** — [Official documentation](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html). Treats tasks as retryable transactions; recommends deterministic reruns, fixed input partitions and upserts over duplicate-prone inserts. **Action:** first implement those properties in a local ingestion function and test reruns/failure recovery; port to Airflow only as an optional extension. Airflow is orchestration overhead, not required for a small portfolio.
13. **dbt data tests** — [Official Developer Hub](https://docs.getdbt.com/docs/build/data-tests). Explains SQL assertions for not-null, uniqueness, accepted values, relationships and custom failing-row queries. **Action:** translate the event-table invariants into three or more tests, including a football-specific coordinate/time test and a join-duplication test. Tests encode your assumptions; they do not validate the definitions themselves.
14. **DuckDB window functions** — [Official SQL documentation](https://duckdb.org/docs/lts/sql/functions/window_functions). Documents `row_number`, `lag`, `lead`, partition/order and frames, suited to local analytical SQL without a server. **Action:** derive event sequence context, previous action, rolling shot count and per-match player rankings. Verify tie ordering and frame behavior; window operations can use substantial memory.

The posting was listed as posted three days earlier, closing 2 November 2026; it describes a club data platform, collection/organization/governance, pipelines for analytics/reporting and support for recruitment, opposition analysis and sports science. **Action:** use those task verbs to review the pipeline portfolio checklist. Status may change after 27 October; this is a role-specific snapshot, not a market count.

## Boundaries and source-use notes

- Use public data for learning and reproducible examples. StatsBomb’s README describes a limited open-data selection and asks for attribution/logo when derived findings are published. Check its current terms; do not assume public access permits unrestricted redistribution or commercial use.
- Never describe synthetic-data scores as evidence of real-model accuracy. Even a sound public-data xG result is specific to the selected competitions/seasons, definitions, sample size and validation split; it cannot establish performance on private club data or commercial systems.
- Event and tracking data differ in granularity and semantics. A common parser/format helps interoperability but does not make providers equivalent. Document coordinate orientation, missingness, timestamp alignment, player identity mapping and conversions.
- A scouting rank is a prompt for further review. Role fit, tactical context, video/live observation, availability, contract, medical and human judgment remain outside many open datasets.
- Keep advanced infrastructure cheap and optional: a local project can show data engineering through repeatable CLI jobs, hashes/manifests, schemas, SQL transformations, tests, logs and failure recovery. Cloud, Airflow, Kafka and paid data vendors are not entry requirements for these exercises.
